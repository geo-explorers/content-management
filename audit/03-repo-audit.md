# 03 — Repository audit synthesis (phase 2)
Sources: audit/architecture-coupling.md, audit/skills-quality.md, audit/notion-tooling-reuse.md, audit/claude-platform-facts.md, audit/best-practices.md, verify/README.md, live gh checks (PR #52, PR #38, geo-editor-agent tree). HEAD fd013a1, 2026-10-09.

## The four questions

### Q1 Could this agent be deployed as a Claude Managed Agent in the future?
**Yes for the MVP (read-only), after ~6 fixes; not yet for anything that publishes.**
- Managed Agents = Agent config (versioned) + Environment (cloud, `limited` networking with `allowed_hosts`) + Sessions; skills are discovered from a mounted GitHub repo only at root `.claude/skills/<name>/`; secrets via vault `environment_variable` credentials (never inside the sandbox); scheduled deployments (cron) with per-run budgets; +$0.08 per running session-hour; beta; needs an API account, not the Max subscription.
- Blockers in today's repo: `.env` with the wallet key loaded at import by `src/functions.ts`; `--env-file=.env` baked into commands; cwd-relative `../../../../src` imports; bun; dependence on the Notion MCP connector; interactive "type publish" gates (and one script that fails OPEN without a TTY); the runtime self-heal from GitHub `main`; skills not at `.claude/skills` root.
- The claim-tagger needs none of `src/`, no wallet, only `NOTION_TOKEN` + Geo read-only + source domains → hostable once the design in 06/08 is followed. Publishing agents need an out-of-band approval record enforced in code (publication contract's `Publish status = Approved` pattern) before hosting.

### Q2 Are we coupling all current/future agents to this repository?
**Today, yes, and the coupling is structural, not incidental.** 7 of 15 skills reference `src/`; 6 assume the repo root as cwd; `sync-skills.sh` installs skills flat so the relative imports break; CLAUDE.md's hard rules load only when the cwd is this repo, so skills installed user-level run WITHOUT the hard rules; agents reference host-specific MCP tool names and repo docs by path. The split already half-exists: `geo-explorers/geo-editor-agent` (public) vendors this repo at fd013a1 with `.claude/agents` + `.claude/skills`, an AGENTS.md entry point and a `sync-upstream.mjs` tool, but it had to copy `src/`, `lib/`, `scripts/` because of the imports, and it pins the commit at which the integrity CI is red.

### Q3 What impact does it have on the team's way of working?
- Good and worth keeping: per-skill content hashing (SKILL-VERSIONS.json), the MD-FILES manifest, dry-run defaults in the mirror scripts, the anchored-entity guard that fails closed, `lib/gql.mjs` never swallowing errors, the S/A/B/C + U0–U3 scales, "say what you could not verify", the Work tracker / QA tracker lifecycle, the Discord change feed.
- Problems: integrity CI is **not a required check and has been red since 2026-09-25** (geo-mirror DRIFT, hand-edited hash); hashes cover `skills/` only, not the `src/`, `lib/`, `scripts/` the skills execute; `.claude/settings.json` auto-approves publish-capable commands and `curl *` with the wallet key loaded; skill descriptions far exceed Claude Code's 1,536-character combined budget and three SKILL.md files exceed 500 lines (triggering and context cost suffer); two Notion identities and two Work trackers are "data problems patched with prose"; Windows is unsupported (rsync, macOS paths, cp1252 crashes in both verifiers); bun vs node guidance conflicts and two lockfiles pin different SDK versions.
- Process smell: the CLAUDE.md "self-heal" rule has an agent download unpinned `main` over HTTPS and overwrite its own instructions and scripts mid-task, with a circular hash check — a supply-chain and prompt-injection vector, not a safeguard.

### Q4 Does the new agent need to reside in this repository?
**No, and it should not.** The user decided D3: content-management becomes a pure skills library; agents live in a new agents repository. Recommendation (08): make `geo-editor-agent` that repository (own it under geo-explorers, fix the URL disagreement, keep its vendoring tool) rather than create a third repo; vendor skills + a new `runtime/` package pinned to a **signed release tag** with a per-file SHA-256 lock verified in CI. Put skills at root `.claude/skills/` (Claude Code and Managed Agents both discover them there) and agents at `.claude/agents/`.

## Prior art found during the audit
- **Draft PR #52 — `geo-submission-review` v0.6.2** (mufasasa, 2026-10-03, +1,843 lines, 56 tests): a bounty-submission review skill. Stage 0 scans proposals per space, resolves curators, reads the proposal entity's **`Bounties` relation** (the bounty↔proposal link exists on Geo when curators set it), fetches `proposalActions.contentUri` from IPFS with a cache, `decodeEdit`s payloads, groups a curator's proposals into persistent "cases", produces review JSON with the six Review-finding fields, publishes reports to the datasets space via geo-publish, drafts curator replies and applies editor-approved votes. The three example evaluations the user supplied match its output format and dates. Issues: labelled non-actionable yet it publishes and votes; a shared skill embeds one editor's standing authorization ("Mohammed has authorized…"), Discord policy, point/payout rules and scheduling policy; SKILL.md is very long and prose-dense. **Use its stage-0/evidence runner as the collect/reconstruct module of the big-picture design; strip policy and authorization into config; keep publishing and voting as separate actionable, human-gated steps.**
- PR #38 (open since 2026-09-01): trim `main` to 5 confirmed skills — signals the team already distrusts part of the skill set.
- The `Bounties` relation on proposal entities + `proposals(filter:{proposedBy})` resolve most of the "Need more info" item: linkage = explicit relation when present, else curator+window grouping, else editor-supplied list.
