Geo Review Agent Blueprint

From a claim tagger that works inside the Notion mirror today, to a bounty-submission reviewer that reads proposals from Geo tomorrow. Interview findings, repository audit, execution loops, skeletons for both stages, two execution modes, and the repository split.

What this design recommends

Build the MVP as a deterministic Node pipeline with one model-judged step, run it in two interchangeable modes (Claude Max session or Claude API), write proposals into four agent-owned Notion columns, and let human confirmations become the gold set. Grow it into the bounty reviewer by adding a collect-and-reconstruct module that already exists in draft form. Move all agents out of content-management into the existing geo-editor-agent repository, pinned to signed releases of the skills library.

Decisions you asked me to document

  • D1 The MVP applies only the 13 tags with Status = Verified. The 14 Proposed tags and the two undefined duplicate tags stay out until the taxonomy marks them verified. The rubric loader filters at run time, so promoting a tag in Notion makes it live without a code change.
  • D2 Ontology reviews for "new types and properties" bounties reuse the ontology-advisor skill and its ONTOLOGY.md until the promised documentation arrives. Its live scripts call a retired endpoint, so only its judgment text is reused, not its helpers.
  • D3 content-management becomes a pure skills library. Agents live in a separate repository. The recommendation is to adopt geo-editor-agent as that repository rather than start a third one.

How "verify" is defined for the MVP

You ranked rule compliance first, then "do the sources contain the position", then taxonomy quality. For the MVP the rules are the taxonomy's own decision rules, applied by the agent. Editors may add context about a dataset but never new tags or rules. Every row gets per-tag verdicts with per-tag confidence, a note with evidence quotes, and a state an editor can filter on.

Debate claims cannot be true or false. The agent therefore never asserts truth. It asserts that the source does or does not contain the position, or that it cannot tell.

What was verified live

  • All six resources were reachable: two Notion databases, the Agent Composition catalog with its five databases, two bounty pages through the Geo API, and three evaluation pages through geo-query.
  • Proposal contents are readable without the Curator site: proposal → IPFS content URI → GRC-20 decoder. Tested on a rejected Crypto proposal; the claim text came back verbatim.
  • Claim sources resolve to Article entities carrying a Web URL property, forty claims per GraphQL batch, under a minute for the whole table.
  • The Notion MCP connector hit the workspace query limit during this session. Bulk work must use the integration token.

What is still open

  • Need more info How a submission is tied to its bounty and proposals. Proposal entities can carry a Bounties relation, and a draft skill already groups proposals by curator and window, so the design isolates this behind one adapter with four fallbacks.
  • The tagger calibration report the taxonomy cites is not visible to the connected Notion account. Optional.
  • Whether claude -p headless runs draw on the same Max usage windows is not documented. Treat it as yes.

Repository audit

Five audits ran: architecture and coupling, skill quality and security, Notion tooling reuse, Claude platform facts, and external best practices. The repository is a monolith wrapped in skills. Its safety story is mostly prose, and the harness configuration undercuts the prose.

The four questions

Could this agent run as a Claude Managed Agent?

Yes for the read-only MVP, after six fixes. Not yet for anything that publishes.

Managed Agents mount one GitHub repository and discover skills only at its root .claude/skills/, one directory deep. Secrets come from a vault as environment variables and never enter the sandbox. Networking can be restricted to named hosts. Scheduled deployments run on cron with a budget. Pricing is standard token rates plus $0.08 per running session-hour, and it needs an API account rather than the Max subscription.

Blockers today: the wallet key loaded at import by src/functions.ts, commands that bake in --env-file=.env, four-level relative imports into src/, the bun requirement, reliance on the Notion MCP connector, interactive "type publish" gates (one script fails open without a terminal), and the runtime self-heal from GitHub.

Are all agents coupled to this repository?

Yes, structurally. Seven of fifteen skills reference src/. Six assume the repository root as the working directory. The sync script installs skills flat into the user's skills folder, which breaks those imports. The hard rules live in a CLAUDE.md that loads only when the working directory is this repository, so skills installed user-level run without the rules.

The split half-exists: geo-editor-agent vendors this repository at commit fd013a1, with .claude/agents, .claude/skills, an AGENTS.md entry point and a sync tool. It had to copy src/, lib/ and scripts/ because of the imports, and it pins the commit at which the integrity check is red.

What is the impact on the team's way of working?

Keep: per-skill content hashing, the Markdown manifest, dry-run defaults in the mirror scripts, the anchored-entity guard that fails closed, a GraphQL client that never swallows errors, the severity and urgency scales, the rule to say what could not be verified, the task and QA lifecycle, and the Discord change feed.

Fix: the integrity check is not required and has been red since 25 September. Skill descriptions far exceed Claude Code's combined 1,536-character budget, so triggering degrades. Three skill files exceed the 500-line guidance. Two Notion identities and two Work trackers are data problems patched with prose. Windows is unsupported. The "self-heal" rule lets an agent overwrite its own instructions from an unpinned branch.

Does the new agent need to live here?

No, and it should not. The library changes rarely and must be reviewed because it holds the safeguards. Agents change often. Different cadence, different repository. The agents repository is also the one a Managed Agent would mount, and the place where the hard rules travel with the agents. See the Repo and deployment tab.

Prior art found during the audit

Draft PR #52, geo-submission-review v0.6.2 (opened 3 October, about 1,800 lines, 56 tests) is a bounty-submission reviewer. It scans proposals per space, resolves curators, reads the proposal entity's Bounties relation, fetches payloads from IPFS with a cache, decodes them, groups a curator's proposals into cases, writes review JSON with the six Review-finding fields, publishes reports to the datasets space and applies editor-approved votes. The three evaluation pages you gave me match its output.

Reuse its stage-0 runner as the collect-and-reconstruct module of the bounty reviewer. Do not adopt as-is: it embeds one editor's standing authorization, Discord and payout policy inside a shared skill, it votes from a skill labelled non-actionable, and its SKILL.md is long and dense.

PR #38 (open since 1 September) proposes trimming main to five confirmed skills. The team already distrusts part of the skill set, which supports the library-plus-agents split.

Execution loops

The MVP loop is a fixed workflow, not an agent deciding what to do next. Code owns every step whose result is knowable without judgment. The model owns exactly one step. A human owns the gate and the final review.

The bounty-review loop

MVP skeleton: the claim tagger

Any Notion table with a title column and a Geo ID column is a valid input. The agent owns four columns, writes nothing else, and never writes Geo.

Orchestrator pseudocode


cfg      = loadConfig(argv)                 // --db --limit 50 --ids --force --mode session|api --model --publish --context
pre      = precheck(cfg)                    // stops with the exact missing thing; creates missing agent columns on --publish
roster   = readRoster(cfg.db)               // Notion REST, paced; every id must be a Claim on Geo
queue    = selectQueue(roster, cfg)         // Agent review state empty, unless --force or --ids; first --limit
claims   = enrichGeo(queue, cfg.space)      // one GraphQL per 40 ids; Sources → Article → Web URL; Unsourced computed
evidence = fetchEvidence(uniqueUrls(claims))// cached by URL hash; status ok | blocked | dead | pdf | timeout
quotes   = extractQuotes(claims, evidence)  // cheap worker; each quote verified as a substring or dropped
batches  = prepareBatches(claims, quotes, rubric, 10)
if (cfg.mode == 'api') judgeApi(batches, cfg) else judgeSession(batches, cfg)   // both write judgments/*.json
judg     = loadAndValidate('judgments/', schema)        // invalid → one retry → Error state
plan     = calibrate(judg, claims, cfg.thresholds)      // tags, confidence lines, notes, state
printDryRunReport(plan); if (!cfg.publish) exit 0
receipts = writeNotion(plan, cfg)           // allowlist of four columns; one PATCH per row; 2.5 req/s
diff     = readBack(plan, cfg)              // "N rows checked, 0 remaining differences" or the list
writeLedger(); printSummary(diff)           // queued = proposed + needs_editor + not_checkable + error


  

    

      
Calibration rules

      
    
        
  • Floor 0.60. A tag below the floor is not written; its reason goes to notes as [below floor].
    • 
        
  • Band 0.60 to 0.75: the tag is written and the state becomes Needs editor, with any editor question appended.
    • 
        
  • A counterpart pair writes exactly one side if confidence clears the floor, otherwise neither and Needs editor.
    • 
        
  • cannot_tell always routes to Needs editor.
    • 
        
  • Rows with no sources get Unsourced plus the four pair tags; Improperly sourced is cannot_tell with the reason; state Proposed.
    • 
        
  • A schema failure after one retry leaves the row in Error with no tags written.
    • 
      

    

    

      
Editor loop

      
    
        
  1. The agent sets Needs editor and writes QUESTION FOR EDITOR in the notes.
    2. 
        
  2. The editor answers in Review notes or sets the verified tags and Review status.
    3. 
        
  3. The next run with --rerun needs-editor passes the editor's note as context for that claim only and re-judges it. The ledger records it as a rerun.
    4. 
      

      
No new tracker statuses are invented. Everything lives in the mirror's agent columns.

    

    

      
Evaluation harness

      
    
        
  • Bootstrap: a stratified 100-row set labelled by two editors. Cohen's kappa per tag. A tag with kappa under 0.6 gets its rules sharpened in Notion before the model is judged.
    • 
        
  • Living gold set: rows with Review status = Reviewed and non-empty verified tags. Human confirmation is the label.
    • 
        
  • Reports: precision, recall and F1 per tag with Wilson 95% intervals; confusion per counterpart pair; calibration bins; cannot_tell and Needs-editor rates.
    • 
        
  • Bar before unattended runs: F1 at or above 0.85 on the four pairs; precision at or above 0.90 on Improperly sourced.
    • 
        
  • Every row carries model, rubric hash and prompt version so any score traces to a configuration.
    •

Execution modes

  
One pipeline, two judge adapters. Every deterministic step is the same code and the same files in both modes. Only the step that asks a model for judgment is swapped. This is what keeps the MVP portable to a hosted agent later.


  

  

    

      
Mode A · session mode

      
An editor says "tag claims in this table, limit 50" in the agents repository. The claim-tagger subagent runs steps 1 to 6 as Bash commands, then spawns up to five claim-judge subagents (tools: Read and Write only; model configurable, default Sonnet 5.5), one per batch file. Each writes one judgment file per claim and never touches the network or Notion. The orchestrator validates, prints the dry-run report, waits for the literal word publish, then writes and reads back.

      
Why subagents here: context isolation (the orchestrator never sees page text), parallelism, and a cheaper model for the judge role.

      
Constraints: the Max plan has a five-hour window and a weekly cap shared across Claude and Claude Code, and subagent calls draw on them. Hence batch 50 by default. Unattended options exist: claude -p with a one-year token from claude setup-token, or Routines (cloud-scheduled, minimum one hour, counts against the subscription). The docs warn that --bare may become the headless default, which would bypass subscription login, so treat unattended subscription runs as provisional.

    

    

      
Mode B · API mode

      
node scripts/run.mjs --mode api --limit 500 --model claude-opus-5-5 --publish. One request per claim: a system block holding the rubric with a one-hour cache, the claim and verified quotes as the user turn, output_config.format set to the judgment schema, effort medium, max tokens 2,000, concurrency 4, SDK retries, and server-side refusal fallbacks.

      
--batch sends the same requests to the Message Batches API at half price. Results are keyed by custom_id = geoId, never by position, and the run resumes from a state file if interrupted.

      
Constraints: needs an API key or an ant auth login profile and a budget owner. The cached rubric pays off only within its TTL window, so keep concurrency at two or more.

      
Default model: Opus 5.5, because the directive is to downgrade only when measured. The eval harness decides whether Sonnet or Haiku holds quality.

Big picture: the bounty-submission reviewer

  
Advisory by design. It reads a bounty, collects the curator's proposals, reconstructs what was submitted, runs five checks, and drafts a curator-facing review. A human approves before anything is published or voted.

Default output is a Notion page: header with the bounty link, curator, proposals reviewed as governance links, last reviewed in UTC, verdict; an outcome-first overview of three to five bullets; a findings table in the Review finding shape plus severity, tag and confidence; and a section for what could not be verified. The same findings can be published as Review finding entities in the datasets space through geo-publish after a human approves, as the three example pages were. Follow-up reviews prepend a follow-up block, as the Afghanistan review does.

  
PR #52 shows that proposal payloads are retrievable and decodable at scale (a pilot grouped 45 proposals into four cases), that the six-field finding format renders well on Geo, and that a recorder can reject non-verbatim excerpts mechanically. It also shows what to avoid: policy and one editor's authorizations baked into a shared skill, and votes from a read-only skill.







  
Repository design and deployment

  
Two repositories, one direction of dependency. The library holds skills and the single write path, released as signed tags. The agents repository vendors a pinned copy, verifies it by hash, and is the only repository a hosted agent ever mounts.


  

  
Dependency mechanism

  

    
OptionProsConsFit

    
      
Git submoduleExact pinHostile to non-engineers; drags in the armed root scripts; needs symlinks into .claude/skills, poor on WindowsLow

      
npm packageSemver, lockfile integrity, npm ci in DockerMarkdown skills still need a copy into .claude/skills; needs a publish pipelineGood for runtime/ later

      
Vendored copy + SHA-256 lockSkill diffs are reviewable in PRs; plain files for hosted images; already the team's pattern in geo-editor-agent; reuses skill_versions.pyDuplicated bytes; needs a CI check against hand editsBest for skills

      
sync-skills.shZero setupUnpinned, per-machine, flattens paths, no Windows, no agents, no verificationReject

    

  
Upgrade flow: a pull request in the agents repository bumps skills.lock.json; CI verifies the hashes against the tag and runs the library's linter; reviewers read the skill diff; merge. No agent fetches skills at run time. At start, every agent verifies the lock and refuses to run on a mismatch.
