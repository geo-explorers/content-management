# Notion review feedback

Read for every default review delivery. Use `notion-operations` when available, or the authorized connector's documented identity, pagination and write/readback procedures. Confirm the actual destination and existing content before writing. Reuse a matching review for resubmissions; use a separate page for requested comparison tests. Preserve the submission, comments and human decisions.

## Required page structure

Use **“<Submission or topic> — review feedback”**, zero to two brief introductory bullets and one native table with exactly these headers:

| Entity | Issue | Citations for quality checks | Relevant quote or evidence detail |
|---|---|---|---|
| One linked submitted entity | The exact assertion or omission and a concise explanation of the demonstrated problem | Direct evidence links with useful page/section locators; include the relevant bounty criterion for judgments | A short, faithful source quotation, or clearly labeled field/timestamp detail or paraphrase |

Show **1–5 distinct problems**, prioritizing significance. Show **one specific example per recurring problem**. Keep other affected entities in the internal record. Never replace the entity with a group label, list every affected entity beneath the table, or add a “What to fix” column. Use the exact generic header Entity for sources, stories, posts, claims and dataset rows.

A brief introduction may say: “Please check the content and supporting sources before submitting.” Keep the tone factual, kind and specific. Do not assume dishonesty or manufacture errors. Each row must make sense on its own and preserve the submitted statement's relevant qualifiers.

Use a native simple table for the default fixed list. If the editor explicitly requests filtering, a native database may use the same four visible columns, with controls hidden unless requested. Read the connector's Markdown specification before writing. Use native mentions for Notion entities where supported; never use a child-page tag just to link an existing page.

## Evidence across submission types

- **Factual assertion:** quote the passage establishing the discrepancy, with enough context to avoid misrepresentation.
- **Duplicate:** link both submissions and give comparable submission timestamps and evidence that they cover the same event/item. A matching topic alone is insufficient.
- **Relevance or significance:** cite the actual bounty/space criterion and source content; explain the connection between those facts and the judgment in Issue. Do not present an editorial judgment as a factual contradiction.
- **Missing or structural field:** cite the requirement and exact submitted record; give the observed field value/state. The blank field alone does not establish a requirement to populate it.
- **X posts/blogs:** read surrounding thread/quoted context and apply the actual bounty; an opinion may qualify. Do not import news-only event requirements or arbitrary engagement cutoffs.

Quotes must be exact excerpts from retrieved evidence. Observe source quotation limits; use a short excerpt plus locator or a labeled paraphrase when needed. Do not put paraphrases in quotation marks. Leave unavailable quotations unquoted and supply meaningful evidence detail; missing access stays unresolved internally and is not evidence of a curator defect.

## Exceptions and internal records

If no supported issue is established, create a brief honest review page without an empty or fabricated findings table. Keep any unresolved coverage limits in the editor handoff. Honor explicit requests for another format or delivery location; record that exception internally.

Keep the review brief, inventory, all checks, other affected entities, unshown findings, verification status, severity, technical QA and editor decisions in a separate internal record. Do not append a long audit, affected-item toggle or general incomplete-review disclaimer to the forwardable page. Include uncertainty within an individual row when it changes that finding. A review date may appear at the bottom.

Record each finding's target, original content, criterion, evidence/locator, effect, resolution criterion and history. Keep agent findings separate from human decisions. Preserve dismissals and comments; match reruns by entity and underlying issue without deleting history. Reuse existing internal status/severity schemes. A short report does not imply that omitted items passed.

This approved format takes precedence over a general report template's TOC, executive memo, heading hierarchy or visible quality checklist. Preserve evidence and authorization requirements.

## Completion gate

1. Confirm a saved page exists in the editor's supplied or established review location. Ask for a destination only when it cannot be determined; report access failures accurately.
2. Fetch the saved content using the writing identity. Check title, at most two introductory bullets, exactly one table, the exact four headers, 1–5 findings and one example per recurring problem. Apply the documented no-findings exception when appropriate.
3. Verify each entity and evidence link, quotations/locators, responsibility and relevant qualifiers. Confirm there is no fix column, affected-entity appendix or internal audit, and that human records are preserved.
4. Inspect layout when available: readable widths, wrapped text, clickable evidence. Verify requested filters. Report visual inspection only when actually performed.
5. Fix any mismatch and read back again. Return the saved page link as the main deliverable. If saving failed, label delivery incomplete; do not substitute a chat/file draft and claim success.

For a timeout or unknown write outcome, inspect the parent and search for the intended page before retrying. Page creation does not authorize sending it to the contributor.
